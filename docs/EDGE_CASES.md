## 5.1 🔧 죽은 키 — 화면을 걷어냈는데 문구가 남았다 (2026-09-09)

| | |
|---|---|
| **증상** | 화면은 멀쩡하다. `home.today.reviewCount` · `knowledge.tags.empty` 가 두 언어에 그대로 남아 **아무도 안 부르는 문구**가 됐다 |
| **원인** | 디자인 패스에서 홈의 카운트 문구를 바꾸고(`count` 로 이름이 바뀜) 태그 빈 상태를 지우면서, 화면만 고치고 리소스를 안 지웠다 |
| **왜 안 걸렸나** | 🔴 `check:i18n` 의 ①②는 **언어끼리만** 대조한다. 두 파일에 **대칭으로** 남아 있으면 차이가 0 이다. ⑤(없는 키)는 *부르는데 없는* 경우만 보므로 반대 방향은 못 본다 |
| **사각 닫기** | 축 **⑥ 죽은 키** 신설(`PLANNED` 예외는 이유 필수 · 예외가 낡으면 그것도 FAIL). 변이 확인: 죽은 키 심기 → FAIL · `PLANNED` 키 삭제 → *"예외 낡음"* FAIL |
| **왜 중요한가** | 화면은 안 깨지므로 **영원히 안 들킨다.** 대신 언어를 15개로 늘리는 날 죽은 키 하나가 **번역 15건**이 된다 |

★ 같은 날 반대 방향(양쪽에서 **지워서** 화면이 키 문자열을 뱉을 뻔한 것)도 겪었다 — 축 ⑤ 가 그것이다.
**두 파일을 대칭으로 틀리면 대조 검사는 침묵한다**(`I18N_SYSTEM.md` §5.2).

## 7. 🔧 소스에 NUL(0x00)이 박혔다 — 기능은 멀쩡했다 (2026-09-09)

| | |
|---|---|
| **증상** | 없다. `features/backup/merge.ts` 의 열쇠 구분자가 공백이 아니라 **NUL 문자**였는데 병합이 정상 동작했다 |
| **원인** | 파일을 쓸 때 구분자 한 글자가 `0x00` 으로 들어갔다. 열쇠를 잇는 데만 쓰이므로 **어떤 값이든 결과가 같다** |
| **왜 안 걸렸나** | 🔴 `tsc`·`lint`·`check:backup`(왕복 · 합치기 · 거부 전부) 이 **모두 초록이었다.** 동작이 안 바뀌니 동작을 재는 검사로는 영원히 안 잡힌다 |
| **잡은 것** | `check:chars` — 바이트로 읽는 유일한 가드다. 형제가 정규식에 `0x08` 이 박혀 19일간 죽어 있던 사고(`I18N_SYSTEM.md` §5.1)와 **같은 종류**다 |
| **수정** | `const SEP = '\\u0000'` 로 **이스케이프를 소스에 적는다.** 값은 그대로고 소스는 ASCII 로 남는다 |

★ 이 항목의 값은 수정이 아니라 **"기능 테스트가 전부 초록이어도 소스는 오염될 수 있다"** 는 사실이다.
그래서 `check:chars` 는 다른 가드가 아무리 늘어도 빠지지 않는다.

## 7.1 🔴 미리보기 숫자가 왜 사각이었나

파일에 tombstone 을 싣기로 한 것(§1)과 미리보기 숫자를 `배열 길이`로 잡은 것이 **각각은 맞았다.**
둘이 만나는 자리에서만 틀렸고, 그 자리를 재는 검사가 없었다 → 가드에 축(미리보기 수)을 하나 더 세웠다.
★ **"둘 다 맞는데 만나면 틀리는 곳"** 은 단위 검사로는 안 나온다. 화면에서 한 번 보는 값이 여기 있다.

### 9.1 🔴 왜 이 결함은 화면으로 못 잡나

알림은 **안 오는 것도, 두 번 오는 것도 사용자가 말해 주지 않는다.** 앱 화면에는 아무 흔적이 없다.
그래서 이 축의 검증은 **기기 상태를 직접 읽는 것**(`dumpsys alarm` · `dumpsys notification`)이고,
그건 스크린샷보다 값이 크다. 백업의 `sqlite3` 조회와 같은 성격이다(§7.2·§8).

★ 이번 세션에서 **화면이 멀쩡한데 틀린 것**을 세 번 만났다:
죽은 i18n 키(§5.1) · 소스의 NUL(§7) · 알림 이중 예약(§9). 셋 다 잡은 것은 **바이트·기기 상태를 직접 읽는 검사**였다.

## 10. 🔧 순환 import — 실기기에 처음 올린 날 번들이 알려줬다 (2026-09-09)

| | |
|---|---|
| **증상** | 없다. 앱은 정상 동작했다 |
| **원인** | `knowledge/repo → review/repo`(`scheduleNewCard`)와 `review/repo → knowledge/repo`(`thoughtsOf`)로 고리가 닫혀 있었다 |
| **왜 안 걸렸나** | 🔴 `tsc`·`lint`·가드 7종이 **전부 초록**이었다. 순환 자체는 타입 오류가 아니고, 지금은 둘 다 **호출 시점에** 함수를 찾아 안 깨진다 |
| **누가 잡았나** | **Metro** 가 번들할 때마다 경고하고 있었다. 에뮬레이터로 볼 땐 로그를 안 읽었고, 폰에 처음 올리며 번들 로그를 보다가 눈에 들어왔다 |
| **위험** | 어느 한쪽이 모듈 **최상위**에서 상대를 쓰는 순간 `undefined` 가 된다. 증상은 "가끔 빈 화면"이라 원인을 못 찾는다 |
| **수정** | `features/knowledge/thoughts.ts` 로 갈라 양쪽이 그것을 보게 했다. 🚫 경고를 끄지 않았다 |
| **재검증** | 폰에서 다시 로드해 **Require cycle 경고 0건** 확인 |

★ 오늘 넷째다. **화면은 멀쩡한데 틀린 것** — 죽은 i18n 키(§5.1) · 소스 NUL(§7) · 알림 이중 예약(§9) · 순환 import(§10).
넷 다 동작을 재는 검사는 놓쳤고, **다른 층을 읽는 것**(바이트 · 기기 상태 · 번들 로그)이 잡았다.

| **증상** | 화면 아래쪽 입력창을 누르면 키보드가 그것을 덮는다. 대표님 폰에서 발견 |
| **원인** | `Screen` 이 `KeyboardAvoidingView` 로 감싸면서 **안드로이드에 `behavior={undefined}`** 를 줬다. 그 값이면 KAV 는 **아무 일도 하지 않는다** |

| **수정** | 조각(diary) → Idea Repository 로 이어진 방식을 승계. 겹침을 **재서** 스크롤 영역을 줄인다 |

### 11.1 왜 "여백 추가" 가 아니라 "영역 축소" 인가

여백을 더하면 **손으로 스크롤해야** 입력창에 닿는다. 영역 자체가 짧아지면 안드로이드 `ScrollView` 가
크기 변화에 맞춰 **포커스된 입력창을 스스로 보이는 데까지 올린다.**

```
겹침 = (Screen 하단 좌표) - (키보드 윗변 좌표)
```

🟢 창이 이미 줄어드는 기기(`adjustResize` 가 먹는 경우)에서는 겹침이 0 이라 아무 일도 안 한다.
**기기를 코드로 나누지 않고 실제로 재서** 판단한다.

⚠ 승계한 코드에 실기기에서 다듬은 흔적이 셋 있다.
- **두 번 잰다**(60ms · 350ms). Gboard 는 뜬 뒤 제안 줄이 붙어 높이가 한 번 더 커진다
- iOS 는 `automaticallyAdjustKeyboardInsets` 가 같은 일을 해서 **안드로이드만** 줄인다(안 그러면 두 번 밀린다)
- 그래도 안 올라오면 포커스된 입력창을 찾아 직접 스크롤하는 보완책

## 12. 🔴🔧 연속일 계산이 틀리면 **멈춘다** — 변이 주입이 찾았다 (2026-09-10)

`check:stats` 를 만들고 변이 10종을 넣어 보다가, 다섯 번째 변이에서 가드가 **실패하지 않고 멎었다.**
30분을 기다려도 아무것도 안 나왔다.

**증상** · `npm run check:stats` 가 출력 없이 영원히 돈다. 실패도 성공도 아니다.

**원인** · 넣은 변이는 `previousDayKey` 에서 `d - 1` 을 `d` 로 바꾼 것 하나다(어제 대신 오늘을 돌려준다).
그러면 `streakDays` 의 `while (days.has(cursor))` 에서 커서가 **줄지 않는다.**

```
cursor = '2026-09-10'  →  days 에 있다  →  n += 1  →  previousDayKey → '2026-09-10'  →  또 있다 → …
```

🔴 **이건 가드의 문제가 아니라 앱의 문제다.** 같은 일이 실기기에서 일어나면 통계 화면이
느려지는 게 아니라 **JS 스레드가 멈춘다.** 화면 전체가 얼고, 사용자에게는 앱이 죽은 것으로 보인다.
숫자가 하나 틀리는 것과 앱이 서는 것은 등급이 다르다.

**수정** · `streakDays` 가 커서가 **반드시 줄어드는지** 매 회 확인하고, 안 줄면 던진다.
날짜 키가 `YYYY-MM-DD` 라 문자열 비교로 충분하다. 잘못된 숫자는 고칠 수 있지만 멈춘 화면은 못 고친다.

**🔴 이전 검사가 왜 못 잡았나** · 셋 다 못 잡을 수밖에 없었다.

| 층 | 왜 침묵했나 |
|---|---|
| `tsc` · `lint` | 타입도 문법도 멀쩡하다. 무한 반복은 타입이 아니다 |
| SELF-TEST | 순서상 `streakDays` 를 **먼저** 부른다. 거기서 멎어서 뒤의 `previousDayKey` 검사에 도달을 못 했다 |
| 변이 주입 자체 | 발화 여부만 봤다. 🔴 **"멈춤"을 실패로 세는 자리가 없었다** |

**사각 닫기** · 변이 주입 스크립트에 `timeout=180` 을 걸어 멈춘 변이를 **침묵이 아니라 사고**로 본다.
그리고 종료 보장을 코드에 박아 두어, 다음에 같은 실수를 해도 화면이 서는 대신 예외가 난다.

★ **이번에도 "화면은 멀쩡한데 틀린 것"의 변주다.** 다만 이번 것은 화면이 멀쩡하지도 않다.
`CLAUDE.md` §16 의 다섯 건보다 한 칸 더 나쁜 자리이고, 찾은 것은 테스트가 아니라 **변이 주입**이다.
