## 1. 처리 경로

```
앱                          Re:Read 서버                       Anthropic
──                          ────────────                       ─────────
지식 카드 1건 (로컬 평문)
  │ POST /api/v1/ai/analyze
  │  { requestId, lang, content, thought?, bookTitle?, page? }
  ▼
                     ① 토큰 검증 → subject_id
                     ② Premium 게이트 (common_server 엔타이틀먼트)
                     ③ 쿨다운 확인 → 월 캡 확인
                     ④ 입력 길이 상한 확인
                     ⑤ 프롬프트 조립
                           │  messages  ───────────────────▶
                           ◀──────────────  { analysis, questions[] }
                     ⑥ refusal · 스키마 검증
                     ⑦ 🔴 성공했을 때만 캡 +1
  ◀ { analysis, questions[], usage }
  ▼
ai_analyses · recall_questions 로컬 저장
```

- `requestId`는 앱이 만든 UUID. **멱등 키이자 원장 PK**다.
- 🔴 **실패는 캡을 소모하지 않는다.** 우리 잘못으로 사용자의 분석권을 잃게 두지 않는다(조각 규율 승계).
- 🔴 **성공 후 앱 저장이 실패해도 서버는 모른다.** 그래서 앱은 응답을 받으면 **먼저 저장하고**
  화면을 갱신한다. 네트워크 응답을 화면에만 쓰고 저장을 미루면 앱이 죽을 때 과금분이 증발한다.

## 2. 🔴 무저장을 규율이 아니라 구조로

가장 흔한 유출 경로는 **에러 로깅에 본문이 섞여 들어가는 것**이다(조각 실증).

- `reportError(error, context)`에 **요청 본문을 절대 넘기지 않는다.** 에러 코드와 `requestId`만.
- 라우트는 `content`·`thought`를 **지역 변수 밖으로 내보내지 않는다.** 응답에 에코하지 않는다.
- 저장하는 것은 **카운터와 토큰 수뿐**이다. 그건 메타데이터이고, 저장한다고 고지한다.
- 🚫 요청/응답 전체를 남기는 디버그 로깅을 프로덕션에 두지 않는다. 개발 env에서만, 그리고
  그 분기를 **env가 아니라 빌드 시점에** 제거한다.

### 2.1 고지 문구

> **"AI 분석을 위해 해당 지식의 원문 · 내 생각 · 책 제목 · 페이지 · 언어 정보가 Re:Read 서버를 거쳐
> AI 제공자(Anthropic)에게 전달됩니다. **Re:Read 서버는 이 내용을 저장하지 않습니다** —
> 저장하는 것은 사용량 카운터와 토큰 수뿐입니다."**

- ✅ 참: "**Re:Read 서버는** 저장하지 않습니다"
- ❌ 거짓: ~~"볼 수 없습니다"~~ — 평문이 프록시를 지나간다
- 🔴 **주어를 반드시 붙인다.** ~~"저장되지 않습니다"~~ 는 **AI 제공자도 저장하지 않는다**로 읽히는데,
  **그건 우리가 근거를 댈 수 없는 문장이다**(2026-09-08 정합 심사 지적).
  Anthropic 의 보관 정책은 우리가 보증할 수 없으므로 **주어를 우리 서버로 못박는다.**
- 🔴 **전달 항목을 빠짐없이 적는다.** ~~"원문과 내 생각"~~ 만 적으면 거짓이다 —
  §1 페이로드에 `bookTitle`·`page`·`lang` 이 함께 간다. **어떤 책을 읽는지가 나간다는 사실**을 빼면 안 된다.
  ⚠ 페이로드를 바꾸면 **이 문장과 처리방침을 같이 바꾼다.** `check:shared` 가 타입은 잡지만 문안은 못 잡는다.
- 🔴 i18n 키를 `ai.notice.*`로 두고 **백업(v1.1)의 `backup.notice.*`와 절대 재사용하지 않는다.**
  백업은 반대다("읽지 못합니다" = 참 / "저장하지 않습니다" = 거짓).

## 3. 분석 출력 스키마

앱과 서버가 **같은 타입 정의를 공유**한다(조각의 `shared/` + `check:shared` 방식 승계 — 어긋나면 가드가 잡는다).

```ts
type ContentType = 'FACT' | 'CONCEPT' | 'OPINION' | 'INSIGHT' | 'ACTION';
type Actionability = 'none' | 'low' | 'high';
type QuestionKind = 'recall' | 'understand' | 'perspective' | 'experience' | 'apply';

interface Analysis {
  contentType: ContentType;
  summary: string;          // 내용 요약
  keyConcept?: string;       // 핵심 개념
  topics: string[];          // 관련 주제 (0~5)
  authorClaim?: string;      // 저자의 주장
  thoughtRelation?: string;  // 사용자의 생각과의 관계 — thought 가 있을 때만
  actionability: Actionability;
}

interface Question {
  kind: QuestionKind;
  question: string;
  expectedPoint?: string;    // 🔴 정답이 아니다. "이런 걸 떠올렸으면 좋겠다"의 요지
}
```

- **질문은 5종을 억지로 채우지 않는다.** 카드 유형에 맞는 것만 만든다(`REVIEW_SYSTEM.md` §4).
  FACT 카드에 `perspective`(반대 근거)를 묻는 것은 나쁜 질문이다.
- `thoughtRelation`은 **내 생각이 있을 때만** 생성한다. 없는데 만들면 지어낸다.
- 스키마 위반 응답은 **버리고 실패로 처리한다**(캡 미소모). 반쯤 맞는 것을 저장하면
  나중에 화면에서 조용히 깨진다.

## 4. 콘텐츠 유형 5종 — 무엇을 가르는 스위치인가

유형은 **라벨이 아니라 동작을 가른다.**

| 유형 | 회상 질문 | 실천 제안 |
|---|---|---|
| `FACT` 사실·정보 | recall | ✗ |
| `CONCEPT` 개념 | recall · understand | ✗ |
| `OPINION` 저자 주장 | understand · perspective | ✗ |
| `INSIGHT` 사용자의 깨달음 | experience · recall | 드물게 |
| `ACTION` 행동·방법 | recall · apply · experience | ✅ `actionability`가 정함 |

🔴 **`actionability = 'high'` 일 때만 [실천해보기]를 띄운다.** 그리고 그것도 **제안**이다 —
사용자가 [넘어가기]를 고르면 그걸로 끝이고, 같은 카드에 다시 묻지 않는다(기둥 3).

## 5. 비용 방어

조각의 3층 구조를 승계한다. 🔴 **앱이 아니라 서버가 판정한다** — 클라이언트 게이트는 우회된다.

| 층 | 테이블 | 무엇 |
|---|---|---|
| Premium 게이트 | (common_server 엔타이틀먼트) | 무료 사용자는 여기서 막힌다 |
| 월 캡 | `ai_usage` | Premium 사용자의 월 분석 횟수 상한 (⚠ 미결정 E) |
| 쿨다운 | `ai_cooldowns` | **연속 실패 시 잠금** — refusal·upstream 오류 폭주 방어 |
| 일일 상한 | `ai_calls`의 `day` 축 | 하루 폭주 방어 |

### 5.1 원장 설계 주의 (조각에서 그대로 가져오는 규율)

- 🔴 **캡 소모는 조건부 UPDATE로 한다.** 읽고→쓰면 동시 요청 둘이 **모델을 두 번 부른다**(돈이 두 번 나간다).
- 🔴 **`ai_cooldowns`를 `ai_usage`에 섞지 않는다.** 실패를 같은 테이블에 넣으면 캡 계산이 틀리고
  UNIQUE의 의미가 사라진다.
- 🔴 **성공만 `ai_usage`에 기록된다.** 그래서 그 행의 존재가 곧 "이건 이미 분석했다"의 진실이다.
- 🔴 **Re:Read의 캡 축은 기간이 아니라 건수다.** 조각의 `uq_ai_usage_period(subject, kind, periodKey)`를
  그대로 베끼면 안 된다 — 우리는 같은 달에 카드를 여러 개 분석한다.
  → `ai_usage`는 `(subject_id, period_key)` 당 한 행 + `count` 컬럼으로 간다.

### 5.2 입력 길이 상한

한 챕터를 통째로 붙여넣는 사용자가 반드시 있다. 상한을 서버가 강제하고,
초과 시 **분석 전에** 명확히 안내한다(캡 미소모). 상한값 ⚠ 미결정 — Phase 8 원가 실측과 함께.

## 6. 프롬프트

- `prompt_ver`를 **로컬 `ai_analyses`와 서버 `ai_calls` 양쪽에 남긴다.** 프롬프트를 고친 뒤
  품질이 나아졌는지 가르는 유일한 축이다.
- 🔴 **원문 언어와 응답 언어를 명시적으로 분리해 지시한다.** 사용자 UI는 ko인데 책은 en일 수 있다.
  원문은 en 그대로 인용하고 분석은 ko로 쓰는 식이다(`I18N_SYSTEM.md`).
- 🚫 **분석이 원문을 재작성하지 않게 한다.** `summary`는 요약이지 원문 대체가 아니다 —
  복습에서 공개하는 것은 언제나 **사용자가 저장한 원문**이다.
- refusal(모델 거부) 처리: 실패로 간주하고 캡을 소모하지 않는다. 사용자에게는
  "이 내용은 분석할 수 없었습니다"로 안내하고 **카드는 그대로 유효하다.**

## 7. 🚫 서버가 저장하지 않는 것 — 조각과 다른 점

조각은 품질 피드백을 위해 **생성된 리포트 본문**을 90일 보관한다(`ai_reports`).
Re:Read는 **v1에서 그것을 하지 않는다.**

- 조각은 원격 관측이 0인 앱이라 리포트 품질을 볼 방법이 문의밖에 없었다.
- Re:Read는 **분석 대상이 사용자가 저장한 원문 그 자체**라, 출력만 저장해도 입력이 상당 부분 유추된다.
  ("이 문장의 핵심 개념은 X" 를 보관하면 원문이 무엇이었는지가 드러난다)
- → 🔴 **품질 개선이 필요해지면 그때 별도 결정으로 올린다.** 처리방침 문안이 함께 바뀌는 결정이므로
  조용히 추가하지 않는다. 그때는 **사용자 opt-in**(신고 버튼을 누른 건만)이 출발점이다.

## 9. 엣지 케이스 (v1 착수 시 `EDGE_CASES.md`로 이관)

| 상황 | 기대 동작 |
|---|---|
| 오프라인에서 저장 | 카드는 저장된다. AI 분석은 **나중에** 사용자가 요청 |
| 분석 중 앱 종료 | `requestId` 멱등으로 재요청 시 이중 과금 없음 |

| Anthropic 장애 | 쿨다운 진입 · 저장/복습/실천은 전부 정상 |
