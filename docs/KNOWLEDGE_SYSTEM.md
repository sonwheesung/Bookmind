## 1. 🔴 저장 흐름 — 이 시스템의 존재 이유

기둥 1: **독서를 방해하지 않는다.** 저장 흐름에 필수 입력을 추가하자는 제안은 전부 여기서 기각한다.

```
앱 열기 → [+] → 원문 입력 또는 촬영 → [저장]
                                        └─ 끝. 책도 안 골라도 된다.
```

### 1.1 필수는 `content` 하나뿐이다

| 필드 | 필수 | 왜 |
|---|---|---|
| 원문(`content`) | **O** | 이게 없으면 지식이 아니다 |
| 책 | ✗ | 🔴 나중에 붙일 수 있다. 지금 고르게 하면 흐름이 끊긴다 |
| 페이지 | ✗ | |
| 내 생각 | ✗ | 기둥 6과 충돌하지 않는다 — **쓰는 자리는 항상 열려 있되 강제하지 않는다** |
| 태그 | ✗ | |

⚠ 저장 후 **"책 연결하기" 유도를 한 번만** 보여준다. 반복하면 그게 곧 필수 입력이 된다.

### 1.1.1 🔧 책 고르기 — 칩에서 목록으로 (2026-09-10 · 대표님 지적)

원래는 **칩 한 줄**이었다. 책이 서너 권일 때는 그게 가장 빠르다. 그런데 대표님이 실기기에서
두 가지를 동시에 짚었다.

| 무엇이 문제였나 | 왜 |
|---|---|
| 🔴 **책을 등록할 길이 없다** | 책이 0권이면 칩이 `책 없음` 하나뿐이다. 그 화면에서 책을 만들 수 없어서 |
| 책이 많아지면 못 고른다 | 칩이 줄바꿈으로 쌓여 화면 절반을 먹는다. 스무 권이면 스크롤이다 |

🔴 **앞의 것이 더 나쁘다.** 뒤의 것은 불편이고 앞의 것은 **막다른 길**이다.
설계상 책은 `/books` 에서 만들게 돼 있었는데, 저장 화면에 온 사람은 거기까지 안 간다.

바꾼 것:

```
책        [ 책 없음                      ▾ ]
                ↓ 누르면
          ┌────────────────────────────┐
          │ 책 없음                  ✓ │
          │ 아주 작은 습관의 힘         │
          │ 사피엔스                   │
          │ ────────────────────────── │
          │ + 새 책 등록                │
          └────────────────────────────┘
```

- 🔴 **기본값은 여전히 `책 없음`** 이다(§1.1). 고르라고 요구하지 않는다.
- 🔴 **`+ 새 책 등록`이 목록 안에 있다.** 막다른 길을 없애는 것이 이 변경의 요점이다.
- 🚫 검색창을 지금 넣지 않는다. 스무 권까지는 목록이 더 빠르고, 필요해지면 그때 넣는다.
- ⚠ 이 변경은 `DESIGN_REVIEW.md` 창구를 거치지 않았다. 대표님이 실기기에서 직접 지적한 것이라
  시안 검수가 아니라 **결함 수정**으로 처리했다.

### 1.2 저장 화면은 앱의 첫 화면에서 1탭 거리다

홈 어디에서도 **최대 1탭**으로 저장에 닿아야 한다. 책 목록 → 책 선택 → 저장은 **경로가 아니다**
(책에서 출발하는 경로는 있어도 되지만 기본 경로가 되면 안 된다).

### 1.3 입력 방식

| 방식 | MVP | 비고 |
|---|---|---|
| 직접 입력 | ✅ | |
| 붙여넣기 | ✅ | 전자책·메모 앱에서 옮겨오는 경로. 실제로 가장 많이 쓰일 수 있다 |
| 사진 → OCR | ✅ | §2 |
| 음성 | 🚫 2차 | |

## 2. OCR

✅ **엔진 확정(2026-09-10 · 결정 #20)**: `@react-native-ml-kit/text-recognition`
(Google ML Kit 온디바이스 텍스트 인식). ⚠ 미결정 C 가 닫혔다. 근거와 대가는 §2.1.

방향은 원래 기둥 2에서 도출돼 있었다:

- 🔴 **온디바이스여야 한다.** 책 페이지 사진을 서버로 보내면 "지식이 기기를 떠나지 않는다"가 거짓이 된다.
- 촬영 이미지는 **저장하지 않는다.** 텍스트만 추출하고 이미지는 버린다(사용자가 원문 확인용으로
  남기길 원하면 그때 옵션으로 — v1에는 없다).
- 인식 결과는 **반드시 편집 가능한 상태**로 보여준다. OCR은 틀린다. 틀린 채로 저장되면
  복습 질문까지 오염되고, 그건 사용자가 이유를 알 수 없는 형태로 나타난다.
- 글로벌 출시이므로 **다국어 인식**이 필요하다 — 한국어 전용 엔진은 채택하지 않는다.

### 2.1 ✅ 엔진 — 왜 ML Kit 인가 (2026-09-10)

| 후보 | 판정 |
|---|---|
| **`@react-native-ml-kit/text-recognition`** | ✅ **채택.** 온디바이스 · 한국어·일본어·중국어·데바나가리·라틴 · autolinking |
| `react-native-vision-camera` + 인식 플러그인 | 🚫 카메라 전체를 들여온다. 우리는 **사진 한 장**만 필요하다 |
| Tesseract 계열 | 🚫 학습 데이터를 앱에 넣어야 하고 한국어 정확도가 낮다 |
| 클라우드 OCR(Vision API 등) | 🚫 **기둥 2 위반.** 책 페이지 사진이 서버로 나간다 |

- 🟢 **모델이 기기에 있다.** 네트워크 요청이 0건이라 비행기 모드에서도 되고, 원가가 0원이다.
- 🟢 **autolinking 으로 붙는다.** config plugin 을 쓰지 않으므로 `prebuild` 가 지워도 되돌아온다
  (서명과 다른 자리다 · `BUILD.md` §5.1).

🔴 **대가 하나: 스크립트를 호출마다 골라야 한다.** ML Kit 은 라틴 모델과 한국어 모델이 따로다.
한 장을 두 모델로 동시에 읽지 않는다.

```
기본값 = 앱 언어  (ko → KOREAN · 그 밖 → LATIN)
```

🟢 **한국어·일본어·중국어 모델은 라틴 문자도 함께 읽는다.** 그래서 한국어 책 속의 영어 단어는
기본값 그대로 잡힌다. 반대(라틴 모델로 한글)는 안 된다.
→ ~~인식 화면에 **스크립트 바꾸기**를 둔다. 결과가 이상하면 사용자가 한 번에 다시 읽는다.~~
🔄 **2026-09-14 부터 앱이 자동으로 고른다**(§2.1.1 · 결정 #24). 바꾸기는 링크 뒤로 들어갔다.

🔴 **또 하나: 네이티브 모듈이라 Expo Go 에서 안 돈다.** 개발 빌드나 릴리스 빌드가 있어야 확인된다.
그래서 이 기능만은 **에뮬레이터 Expo Go 로 검증할 수 없다**(`BUILD.md` §2).

#### 🔴 2.1.1 문자는 앱이 자동으로 고른다 (2026-09-14 · 결정 #24)

위의 *"스크립트 바꾸기를 둔다"* 를 바꿨다. 사용자는 문자를 고르러 온 게 아니라 문장을 가져오러 왔다.
🔴 **ML Kit 에는 자동 감지가 없다.** `recognize(uri, script)` 는 스크립트를 반드시 받는다
(기본 LATIN · 라이브러리 `index.ts` · 안드로이드 `TextRecognitionModule.java` 실측).
그래서 **여러 모델로 읽고 우리가 고른다.** 판정은 전부 `features/ocr/compute.ts` 의 순수 함수이고 `repo.ts` 는 부르기만 한다.

```
첫 판독 = 앱 언어 기본값 (ko → KOREAN · 그 밖 → LATIN)
   ↓ 글자를 문자 체계별로 센다 (countScripts)
① 첫 모델 고유 글자 ≥ 판정선              → 끝
② 첫 모델이 비라틴인데 라틴 글자 ≥ 판정선  → 끝 (비라틴 모델은 라틴도 읽는다)
③ 그 밖 → 한국어 → 일본어 → 중국어 → 데바나가리 순서로 이어 읽는다 (방금 읽은 것은 뺀다)
          고유 글자가 판정선에 닿는 모델이 나오면 거기서 멈춘다
   ↓
고유 글자가 가장 많은 결과를 쓴다. 같으면 먼저 읽은 것. 아무도 판정선에 못 미치면 첫 결과.
```

| 모델 | 고유 글자 |
|---|---|
| LATIN | 라틴 문자 |
| KOREAN | 한글 |
| JAPANESE | 가나 + 한자. 🔴 **가나가 0 이면 0** 이다(한자만 있는 페이지는 중국어로 본다) |
| CHINESE | 한자 |
| DEVANAGARI | 데바나가리 |

- 판정선 `AUTO_MIN_CHARS = 8` 은 🔴 **추정치다.** 실기기 사진으로 재기 전까지 근거가 없다.
- ⚠ **이어 읽기에 라틴은 없다.** 라틴 모델은 다른 문자를 못 읽어서 신호가 안 나온다.
- 🔴 **헛짚는 자리를 알고 있다**: 라틴 모델(영어 앱)이 한글 페이지에서 엉뚱한 라틴 글자를 판정선 이상 내면 ①에서 끝난다.
  그래서 칩을 없애지 않고 **"다른 문자로 다시 인식" 링크 뒤로** 숨겼다. 링크를 누르면 칩이 열리고, 고른 문자로 한 번만 읽는다(자동 없음).
- ⏸ 판독 1회 시간 · 헛짚을 때 다섯 번의 체감 시간 · 판정선이 맞는지는 **다음 AAB 에서 실기기로** 잰다.

### 2.2 화면 흐름 (`app/knowledge/scan.tsx`)

🔄 **2026-09-11 에 고르는 방식을 바꿨다**(결정 #22 · 책담 승계).
~~인식한 전부를 편집 칸에 넣고 사용자가 지운다~~ 는 책 페이지에서 **90%를 지우는 일**이 되어
기둥 1 과 정면으로 부딪혔다. 이제 **줄을 눌러 고른다.**

```
[사진 찍기] / [앨범에서 고르기]
      ↓
   인식 (온디바이스 · 문자는 자동 §2.1.1) → 줄마다 **텍스트 + 좌표**
      ↓
사진 위에 줄 박스  ·  탭해서 색칠  ·  (다른 문자로 다시 인식)  ·  [다시 찍기]
      ↓
고른 줄을 읽기 순서로 이어 **편집 가능한 텍스트**로
      ↓
  [이 문장으로 저장]  →  빠른 저장 화면으로 텍스트를 넘긴다
```

- 🔴 **고른 뒤에도 편집 칸을 지난다.** §2 가 *"인식 결과는 반드시 편집 가능한 상태로"* 를 규칙으로 박아 뒀다.
  🟢 **책담도 같다**(`DEV_BUILD.md` — *"추출 문장이 인용란에 채워지고 직접 편집 가능"*).
  ~~"책담은 고른 것을 그대로 넘긴다"~~ 는 **2026-09-11 에 우리가 잘못 적은 것이다.** `ocr.tsx` 만 보고
  `setQuote` 가 어디로 가는지 안 따라갔다. ★ **소스만 읽고 그 프로젝트의 설계 문서를 안 읽은 결과다.**
- 🔴 **좌표가 없는 줄을 버리지 않는다.** ML Kit 이 `frame` 을 안 주는 줄이 있을 수 있고, 그 줄이
  목록에서 사라지면 **사용자가 그 문장을 가져올 방법이 아예 없어진다**(책담이 그렇게 버린다).
  → 좌표 없는 줄이 하나라도 있으면 **전체 텍스트 경로**(`joinBlocks`)를 폴백으로 함께 보여준다.
- 🔴 **이미지를 앱 저장소에 남기지 않는다.** 인식이 끝나면 임시 파일을 **지운다**(§2).
  사진 라이브러리의 원본은 사용자 것이라 건드리지 않는다.
- 🔴 인식 결과가 **비어 있거나 하나도 안 골랐으면 저장 버튼이 잠긴다.** 빈 카드가 생기면 안 된다(§8 엣지).
  그때 문구는 "다시 찍어 보세요"가 아니라 **직접 입력으로 가는 길**이다.

#### 🔴 2.2.1 좌표계가 둘이다 — 책담이 안 닫은 축

ML Kit 이 주는 좌표는 **원본 픽셀** 기준이고 화면은 **표시 크기**로 그린다. 둘을 안 맞추면
박스가 전부 어긋나고, 그러면 사용자는 엉뚱한 줄을 고르게 된다.

```
배율 = 표시 폭 / 원본 폭        (이미지를 폭에 맞춰 세로를 늘려 그릴 때만 참이다)
박스 = { left · top · width · height } × 배율
```

- 🚫 **이미지에 `maxHeight` 를 걸지 않는다.** 거는 순간 위 식이 거짓이 되고 박스가 통째로 틀어진다.
  세로가 길면 화면을 스크롤한다.
- 🔴 **배율 계산을 순수 함수로 둔다.** 화면 안에서 계산하면 가드가 잴 수 없다
  (`common/COACH_MARKS.md` §4 가 같은 이유로 말풍선 자리 계산을 컴포넌트 밖으로 빼라고 적었다).
- 🔴 **EXIF 회전**: 카메라 사진에는 회전 메타가 붙는다. picker 가 준 `width`·`height` 와 ML Kit 이
  읽는 방향이 어긋나면 박스가 90도 돌아간다. **실기기에서 세로·가로로 각각 찍어 확인한다.**
- ⚠ 둘 다 **에뮬레이터로는 안 보인다.** 카메라가 없고 회전 메타도 안 붙는다.
  `common/COACH_MARKS.md` §3 이 *"에뮬에서는 완벽하고 실기기에서만 깨진다"* 고 적어 둔 그 자리다.

🟢 **책담 스펙이 같은 함정을 독립적으로 적어 뒀다**(2026-09-11 확인 · `책담_SPEC.md` §5):
> *"이미지 리사이즈/회전 보정 후 OCR에 넘길 것(expo-image-manipulator)."*

🔴 **그런데 구현에는 없다**(소스 grep 0건 · `DEV_BUILD.md` 가 *"(선택) … 회전 보정 등 정교화"* 로 남겨 뒀다).
즉 **스펙은 알고 있었고 코드는 못 따라간 축**이다. 우리는 그 자리를 처음부터 열어 두고 시작한다.

#### 2.2.2 책담 스펙이 가진 것 중 **우리가 다르게 가는 것**

| 무엇 | 책담 스펙 | 우리 |
|---|---|---|
| 고르는 동작 | 탭 **+ 드래그**(형광펜) | **탭만.** 드래그는 책담도 구현 못 했다(`DEV_BUILD.md` 남은 작업). 필요해지면 그때 |
| 인식 단위 | block → line → **element** | **line 까지.** element(낱말) 단위는 고를 것이 너무 잘게 쪼개진다 |
| 원본 사진 | `page-photos` 버킷에 **선택적 보관** | 🚫 **안 남긴다.** 기둥 2 이고 §2 가 이미 정했다. 서버 자체가 없다 |

- 🔴 저장은 이 화면에서 하지 않고 **빠른 저장 화면**으로 넘긴다. 책·페이지·태그를 붙이는 규칙이
  거기 한 벌만 있어야 한다. 두 벌이 되면 한쪽이 반드시 늙는다.
- `source_type` 은 `'ocr'` 로 저장한다(스키마에 이미 있다).

```
│  중요하다."                         │
│                                     │
│ 《아주 작은 습관의 힘》 · 123p        │   ← book · page (없으면 안 보임)

│ 내 생각                             │   ← 기둥 6: 원문과 동등하게 둔다

│  이유를 생각하게 됐다."              │

│    [실천해보기]  [넘어가기]           │

```

### 3.1 🔴 페이지는 **숫자일 때만** 단위를 씌운다 (2026-09-11)

`page` 는 자유 텍스트다(`DATABASE.md` §2 — `"123p"` · `"3장"`). 그래서 화면이 접사를 무조건 붙이면
`42p쪽` · `3장쪽` 이 된다. 실기기에서 실제로 그렇게 떴다(`EDGE_CASES.md` §14).

```
42   →  42쪽 · p.42        숫자다. 씌운다
42p  →  42p               사용자가 이미 단위를 썼다. 그대로 둔다
3장  →  3장               쪽이 아니라 장이다. 그대로 둔다
```

- 🚫 **입력을 숫자로 막지 않는다.** 동양 고전은 쪽이 아니라 장으로 세고, 막으면 저장 흐름에
  규칙이 하나 는다(기둥 1). 고치는 자리는 **입력이 아니라 표시**다.
- ⚠ 영어는 접사가 **앞**에 온다(`p.42`). 그래서 *"안 붙이면 된다"* 로는 못 고친다.
  자리는 i18n 이 정하고, 우리는 **씌울지 말지**만 판정한다(`features/knowledge/compute.ts`).
- 가드 `npm run check:knowledge` 가 잰다.

---

- 🔴 **AI 분석이 없어도 카드는 완결이다.** 무료 사용자에게 "분석하려면 결제" 자리를 크게 두지 않는다 —
  카드가 미완성으로 보이면 기둥 6("생각을 안 써도 완결")과 함께 무너진다.
- 내 생각은 **여러 개 쌓인다**(1:N). 시간이 지나 다시 읽고 덧붙이는 것이 제품 컨셉이다(기획서 §3).
  UI는 최신 것을 보여주고 나머지는 접는다.

## 4. 책

### 4.0 🔴 책 목록 순서 — 최근에 쓴 책이 위로 (2026-09-10)

```
정렬 = 그 책에 마지막으로 문장을 저장한 시각 (없으면 책을 등록한 시각), 최근 순
```

🟢 **지금 읽는 책이 저절로 맨 위에 온다.** 사람은 한 번에 한두 권을 읽고, 그 책에 문장을 넣는다.
그래서 이 규칙 하나로 "많아지면 고르기 어렵다"가 거의 사라진다.

🚫 **수동 순서(`sort_order` 컬럼)를 만들지 않는다**(2026-09-10 대표님 선택).
만들면 마이그레이션이 붙고, 무엇보다 **사용자가 관리해야 할 것이 하나 는다.**
책이 늘수록 관리 비용도 같이 느는데, 자동 정렬은 반대로 책이 늘어도 비용이 0 이다.

⚠ 대가: **"내가 정한 순서"를 못 만든다.** 즐겨 쓰는 책을 위에 고정하고 싶어지면 그때
`pinned_at` 컬럼 하나로 연다. 지금 미리 만들지 않는다.

🔴 **파생값이라 저장하지 않는다**(`DATABASE.md` §4). 매번 `knowledge.created_at` 의 최대값으로 잰다.
지운 문장은 안 센다. 지운 것 때문에 책이 위로 올라오면 그건 틀린 화면이다.

### 4.1 상태 3종

`wish`(읽고 싶음) → `reading`(읽는 중) → `done`(완료). 되돌릴 수 있다.

⚠ **상태 전이를 자동화하지 않는다.** "지식을 저장했으니 읽는 중으로 바꿔줄까요?" 같은 제안도 v1에는 없다 —
Idea Repository가 같은 종류의 자동 연동을 기획 단계에서 제외했다.

### 4.2 책 상세 = 그 책에서 나온 지식의 중심

```
책 제목
저자                        읽는 중

저장한 지식 18 · 내 생각 7 · 복습 완료 14 · 실천 3
```

🔴 이 숫자들은 **파생값이다. 저장하지 않고 매번 센다**(`DATABASE.md` §4).

### 4.3 🔴 책을 지워도 지식은 남는다

`book_id`를 NULL로 끊을 뿐 캐스케이드 삭제하지 않는다(`DATABASE.md` §3).
**지식은 책보다 오래 남는 것이 이 제품의 전제다.**
삭제 확인 다이얼로그에 "지식 18개는 그대로 남습니다"를 명시한다.

---

### 4.4 독서 진행률 (결정 #17 · 2026-09-09)

**받는 것은 두 값뿐이다** — 총 페이지, 읽은 페이지. 비율은 계산한다.

```
읽는 중          72%
                 ▓▓▓▓▓▓▓░░░   180 / 250쪽
```

- 🔴 **비율을 저장하지 않는다**(`DATABASE.md` §4). 저장하면 두 값과 어긋나는 순간이 오고,
  그때 어느 쪽이 맞는지 판정할 수 없다.
- ⚠ **둘 다 선택 입력이다.** 총 페이지를 모르면 진행률 줄이 **아예 안 보인다** —
  0%로 보여주지 않는다. 0%는 "안 읽었다"이지 "모른다"가 아니다.
- 🚫 **상태를 자동으로 바꾸지 않는다**(§4.1 그대로). 100%가 돼도 `done` 으로 넘기지 않는다 —
  다 읽고도 완료로 두지 않는 사람이 있고, 그건 그 사람의 판단이다.
- 🚫 **독서 목표(주 N권 등)는 넣지 않는다.** 진행률은 현황이고 목표는 압박이다(기둥 5).
- ⚠ 읽은 쪽이 총 쪽보다 크면 **100%로 자른다.** 입력을 막지는 않는다 —
  개정판·전자책에서 쪽수가 어긋나는 일이 실제로 있다.

## 6. 검색

MVP는 한 쿼리 LIKE(원문 · 내 생각 · 태그 · 책 제목). 디바운스 **350ms**.
FTS·유사도 검색은 2차(기획서 §24 "기존 지식과의 연결").

### 6.1 네 축 · 결과 단위는 **지식 카드**

| 축 | 어디 |
|---|---|
| 원문 | `knowledge.content` |
| 내 생각 | `thoughts.body` |
| 태그 | `tags.name` |
| 책 제목 | `books.title` |

**어느 한 축이라도 맞으면 그 카드가 나온다.** 결과는 언제나 카드 목록이고, 태그나 책이 아니다.
🔴 **어느 축에서 맞았는지 함께 보여준다.** 원문에 없는 말로 카드가 나오면
사용자는 *"왜 이게 나왔지"* 부터 해석하게 된다. 그건 검색이 아니라 수수께끼다.

### 6.2 🔴 `%` 와 `_` 를 이스케이프한다

SQLite `LIKE` 에서 `%` 는 **아무 문자열**, `_` 는 **아무 한 글자**다.
사용자가 `100%` 를 치면 `%` 가 와일드카드가 되어 **전부 걸린다.** 오류가 안 나고 조용히 틀린다.

```sql
... WHERE content LIKE ? ESCAPE '\'      -- 패턴은 코드에서 만들어 넘긴다
```

- 입력에서 `\` · `%` · `_` 앞에 `\` 를 붙인 뒤 `%…%` 로 감싼다. 순서가 중요하다(`\` 를 먼저).
- ⚠ **책 문장에는 `%` 가 실제로 나온다**(통계·경제서). 가상의 문제가 아니다.
- 가드가 이 축을 잰다(§6.5).

### 6.3 조회 규칙

- 🔴 **네 축 전부 `deleted_at IS NULL`** 이다. 지운 생각으로 지운 카드가 되살아나면 안 된다.
- 🔴 **태그·생각은 조인이 아니라 `EXISTS` 다.** 조인하면 태그 수만큼 카드가 늘어나고,
  그걸 `DISTINCT` 로 접으면 **어느 축에서 맞았는지를 같이 고를 수 없다**(§6.1 이 그걸 요구한다).
  `EXISTS` 는 중복을 애초에 안 만든다. 책 제목만 `LEFT JOIN` 인데 책은 카드당 하나라 늘지 않는다.
- 정렬은 **최근 저장 순**(`created_at DESC`). 🚫 관련도 점수를 만들지 않는다.
  LIKE 에는 점수가 없고, 만들면 그때부터 그 점수를 설명해야 한다.
- 대소문자: SQLite `LIKE` 는 ASCII 만 무시한다. 한국어는 대소문자가 없어 영향이 없다.

### 6.4 빈 검색어

- 공백만 있거나 비어 있으면 **아무것도 조회하지 않는다.** 전체 목록을 뿌리지 않는다.
- 그 자리는 빈 화면이 아니라 **최근 저장**으로 채운다(홈과 같은 원칙 · §7).

### 6.5 가드 — `npm run check:search`

| 축 | 무엇을 잰다 |
|---|---|
| ① 네 축 | 원문·생각·태그·책 제목 각각으로 그 카드가 나오나 |
| ② tombstone | 지운 카드·지운 생각·지운 태그 연결이 결과에 **안 나오나** |
| 🔴 ③ 이스케이프 | **`%` 하나**로 검색했을 때 전부 나오지 않나 · **`_` 하나**로 검색했을 때 0건인가 |
| ④ 중복 | 태그와 원문에 동시에 맞아도 카드가 **한 번만** 나오나 |
| ⑤ 빈 검색어 | 결과가 0건인가(전체를 뿌리지 않나) |
| SELF-TEST | 판정 함수가 살아 있는지 **먼저** 증명한다(exit 2) |

🔴 **③ 을 `100%` 로 재면 아무것도 안 지킨다**(2026-09-10 변이 주입에서 드러났다).
이스케이프를 통째로 걷어내도 패턴이 `%100%%` 가 되어 결국 *"100 이 든 행"* 만 나오므로
검사가 그대로 초록이다. 와일드카드가 새는지를 보려면 **검색어가 와일드카드 하나뿐**이어야 한다.
`%` 하나는 새는 순간 전체를 긁어 오고, `_` 하나는 새는 순간 한 글자 이상인 행 전부를 긁어 온다.
사람이 실제로 치는 `100%` 는 그 옆에 **양성 대조**로 같이 둔다.

### 6.6 화면 (`app/search.tsx`)

```
‹  검색
   [ 검색어                                   ]

   원문                                        ← 맞은 축
   "목표보다 시스템이 중요하다"
   아주 작은 습관의 힘

   내 생각 · 태그
   "환경을 바꾸면 행동이 쉬워진다"
```

- 입력은 **자동 포커스**다. 검색 화면에 들어와서 한 번 더 탭하게 만들지 않는다.
- 디바운스 350ms(§6). 한 글자마다 조회하면 목록이 떨린다.
- 맞은 축은 결과마다 **한 줄로** 보여준다(§6.1). 원문 · 내 생각 · 태그 · 책 순서다.
  기둥 6 이 요구하는 순서이고, 화면과 코드가 같은 배열을 쓴다.
- 🚫 결과 개수를 크게 띄우지 않는다. `12건` 은 성취가 아니다.
- 빈 검색어일 때는 **최근 저장**을 그대로 둔다(§6.4). 빈 화면을 만들지 않는다.
- 결과가 0건일 때만 *"찾는 문장이 없습니다"* 한 줄이다. 🚫 다시 검색하라고 지시하지 않는다.

**진입점은 홈 헤더**다. 🔴 문장이 하나도 없으면 **그리지 않는다**. 검색할 것이 없는 사용자에게
검색 버튼은 기능이 아니라 빈 방으로 가는 문이다(홈의 `책 0 · 문장 0` 을 숨기는 것과 같은 규칙).
